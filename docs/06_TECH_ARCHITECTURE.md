# 06. Техническая архитектура

**Версия:** 2.0 · **Дата:** 2026-11-01 · **Статус:** DRAFT-FOR-APPROVAL · Решения, помеченные **SPIKE**, подтверждаются экспериментом на вехе M0–M1.

## 1. Стек и решения

| Область | Решение | Обоснование |

## 2. Модульная структура C++

```text
Source/
  ScavarCore/          # типы, интерфейсы, лог-категории, данные (ItemDefinition), утилиты
  ScavarGameplay/      # персонаж, компоненты Health/Stamina/Inventory/Equipment, оружие, урон
  ScavarWorld/         # время, погода, зоны, лут (CE), спавнеры
  ScavarAI/            # BT-задачи, перцепция, директор зон, архетипы
  ScavarEconomy/       # торговцы, задания, ledger
  ScavarPersistence/   # SQLite-обёртка, схема, миграции, репозитории
  ScavarUI/            # C++-основа виджетов; сами виджеты — Blueprint (WBP_)
  ScavarServer/        # серверный Target, админ-команды, конфигурация
Plugins/               # только внешние; каждый — в журнале лицензий
```

**Правила зависимостей:** `ScavarCore` ← все; `ScavarGameplay` ← `World`, `AI`, `Economy`; `Persistence` не зависит от геймплея (только от интерфейсов `Core`). Циклов нет.

### 2.1. Библиотека `Sim` (ADR-023)

Вся игровая логика, которую можно проверить без движка, живёт в `Source/ScavarCore/Sim/` на чистом C++20 (без заголовков Unreal, без исключений и RTTI): CSV и данные, ГСЧ, урон и броня, баллистика, выживание, предметы и контейнеры, цены, Central Economy, SQLite-слой. Unreal-модуль `ScavarCore` компилирует эти файлы как есть, а `Tests/Sim/` собирает те же файлы обычным CMake и гоняет тесты с ASan+UBSan: `tools/run_sim_tests.sh`.

Правило: **Unreal-классы — тонкие обёртки** над `Sim` (репликация, ввод, анимация, звук). Формулы, правила и данные в них не дублируются.

> **Ограничение движка.** Цели `Server` и `Client` собираются только из **исходников** Unreal Engine. Лаунчерная версия собирает `Game` и `Editor` (RSK-15). Инструкция — [12](12_FIRST_RUN_WINDOWS.md).

## 3. Сетевая модель

**Принцип.** Клиент отправляет *намерения*, сервер выполняет *действия*.

| Действие | Клиент → Сервер | Проверка сервера |
|---|---|---|
| Движение | Ввод + предсказание (CMC) | Скорость, ускорение, коллизии, допуск позиции |
| Стрельба | `ServerFire(weapon_id, t, aim)` | Владение, патрон в магазине, RPM, состояние, позиция, откат хитбоксов |
| Инвентарь | `ServerMoveItem(item, dst, x, y, rot)` | Права, габариты, одновременность, вес, инвариант «один контейнер» |
| Лечение | `ServerUseItem(item, zone)` | Наличие, состояние, не прерван |
| Торговля | `ServerTrade(trader, tx_id, ops[])` | Баланс, лимиты, идемпотентность, транзакция |
| Взаимодействие | `ServerInteract(actor)` | Дистанция, линия видимости, состояние объекта |

**Релевантность.** Игроки — 300 м (TUNABLE), ИИ — 150 м, предметы — 60 м. Приватные данные (чужой инвентарь, состояние здоровья, скрытые ИИ) не покидают сервер (AT-046).

**Бюджеты.** Сервер: кадр p95 ≤ 33 мс при 48 игроках и 80 ИИ (AT-044). Клиент: трафик ≤ 80 КБ/с p95 (AT-046). Клиент: 60 fps p1 ≥ 45 (AT-045).

## 4. Данные

```text
data/*.csv  ──[tools/validate]──►  CI check  ──[Editor Python import]──►  DT_/DA_ assets  ──►  runtime
     ▲                                  │
     └── docs/*.md (генерируемые таблицы: tools/gen_tables.py)
```

- CSV — UTF-8, запятая, заголовок; идентификаторы стабильны; удаление строки допускается только через ADR.
- Скрипты импорта лежат в `Content/Python/` (или `Plugins/ScavarTools`); импорт идемпотентен.
- Любая новая числовая настройка получает запись в CSV или `ServerConfig.ini`, а не константу в коде.

## 5. Сохранение

Полная схема — SYS-12. Инженерные требования:

1. Весь доступ к БД — через `ScavarPersistence`; игровой код не пишет SQL.
2. Запись в отдельном потоке (write-behind queue); критичные операции ожидаются синхронно.
3. Тест на инварианты запускается после каждой серии из 100 000 случайных операций над контейнерами (AT-035).
4. Тест отказа: `SIGKILL` сервера во время нагрузки, затем проверка отсутствия дублей (AT-034).
5. Резервные копии — раз в час (`VACUUM INTO` или копия файла после чекпоинта WAL).

## 6. Репозиторий и процесс

```text
scavar/                       # новый репозиторий (старый scavar-game архивируется, ADR-002)
  README.md · CLAUDE.md · CHANGELOG.md
  docs/                       # этот пакет документации
  data/                       # CSV-таблицы баланса
  tools/                      # скрипты проверки, генерации, сборки
  Config/ Content/ Source/    # проект UE (создаётся на M0)
  SCAVAR.uproject
  .gitattributes .gitignore   # Git LFS и игнорируемые каталоги UE
```

| Практика | Правило |
|---|---|
| Ветки | `main` всегда собирается и проходит проверки; функциональные ветки живут не дольше недели; слияние через Pull Request |
| Коммиты | `type(scope): summary` — `feat(combat):`, `fix(inventory):`, `docs:`, `data:`, `chore:` |
| Review | Каждый PR проверяется человеком или независимым ревью; изменения баланса сопровождаются записью в `CHANGELOG.md` |
| Бинарные файлы | Только через Git LFS |
| Тесты | Каждая система выходит вместе с автотестами из [08](08_QA_AND_ACCEPTANCE.md); без них PR не принимается |
| Проверка | `python tools/check_docs.py` — в pre-commit и CI на каждом PR |
| Сборка | `tools/build.ps1` (M0): Editor, Client, Server Win64 Development; логи в `Saved/BuildLogs/` |
| Версии | Семантика: `0.<milestone>.<patch>`; build-id вшивается в клиент и сервер (AT-042) |

## 7. Журналирование и телеметрия

- Категории: `LogScavarCore`, `…Net`, `…Combat`, `…Inventory`, `…Economy`, `…AI`, `…Persistence`.
- Структурный журнал сделок/смертей/выдач (JSON lines) — для расследований и поиска дюпов.
- Минимальная телеметрия сессии: длительность, смерти, встречи, места смерти (для баланса), без персональных данных.

## 8. Безопасность разработки

1. Секреты (ключи EOS, учётные данные) — только в переменных окружения и менеджере секретов CI; в репозитории — никогда.
2. Серверный `ServerConfig.ini` с админ-паролем в репозиторий не коммитится; в репозитории лежит `.example`.
3. Любой RPC, принимающий данные от клиента, имеет проверку диапазона и права; fuzz-тест — часть CI (M5).

## 9. Работа Claude в репозитории

Подробности — [11](11_AI_WORKFLOW.md). Главное:

- Облачная сессия Claude пишет код, данные, тесты, документацию и ведёт Pull Request'ы.
- **Сборку, запуск редактора и PIE-тесты** выполняет либо разработчик на Windows-машине, либо Claude Code, запущенный непосредственно на этой машине (рекомендуется).
- Результаты сборки и тестов (`Saved/Logs`) возвращаются в PR/сессию как артефакты; без логов утверждение «работает» не принимается.
