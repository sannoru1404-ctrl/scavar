# 08. Качество и приёмка

**Версия:** 2.0 · **Дата:** 2026-11-01 · **Статус:** DRAFT-FOR-APPROVAL

## 1. Принципы

1. **Ничего не «работает», пока нет лога.** Утверждение о работе системы принимается только вместе с результатом теста (лог, видео, отчёт).
2. **Тест рождается вместе с правилом.** Каждое правило MUST в [04](04_SYSTEMS_SPEC.md) покрыто хотя бы одним `AT-xxx`.
3. **Баланс — не тест, а гейт.** Числа TUNABLE проверяются плейтестом; они не блокируют код, но блокируют выход вехи.
4. **Дюпы ищем целенаправленно.** Каждая веха имеет сессию «ломаем экономику» ([§4](#4-протокол-охоты-на-дюпы)).

## 2. Виды проверок

| Вид | Инструмент | Когда |
|---|---|---|
| **Юнит** (C++/Python) | UE Automation, `pytest` | На каждый PR |
| **Системные** (сервер + 2 бота) | Gauntlet / Automation | На каждый PR, затем ночной прогон |
| **Нагрузочные** (боты) | Собственные боты на headless-клиентах | Еженедельно с M3 |
| **Фаззинг RPC** | Генератор случайных сообщений | С M5, в CI |
| **Отказоустойчивость** | `SIGKILL` сервера под нагрузкой | Ночью с M1 |
| **Плейтест** | Люди | Конец каждой вехи |
| **Документация и данные** | `python tools/check_docs.py` | На каждый PR |

## 4. Протокол охоты на дюпы

Проводится в конце M1, M3, M4, M5 группой из 2–4 человек в течение полудня. Цель — получить предметы или деньги без законного источника (SYS-04, SYS-09, SYS-10).

1. **Сценарии:** одновременные подборы; перенос предмета при обрыве; торговля и `SIGKILL`; смерть во время сделки; выход в момент перемещения; рестарт при крафте; повторная отправка запросов; реконнект на вытеснение.
2. **Инструменты:** журнал сделок, сверка суммарных количеств предметов в БД до и после, инвариант контейнеров.
3. **Результат:** отчёт «найдено / исправлено». Любая находка блокирует выход вехи.

## 5. Серьёзность ошибок

| Класс | Определение | Срок |
|---|---|---|
| **S0** | Дюп, потеря данных, краш сервера, эксплойт с серверной стороны | Блокирует релиз; исправление немедленно |
| **S1** | Нарушение правила MUST, крупная ошибка боя/сети | В текущей вехе |
| **S2** | Заметная ошибка, есть обход | До выхода следующей вехи |
| **S3** | Косметика, текст | По возможности |

## 6. Плейтест: протокол

1. Группа 8–12 человек; запись экрана и телеметрия.
2. Сессия 60–90 минут; затем опрос (5 вопросов): «понял ли цель», «когда было интересно / скучно», «когда было несправедливо», «хочешь ещё?», «что бы изменил».
3. Фиксируем: время до первого оружия, до первой встречи, число смертей, места смерти.
4. Выводы оформляются в `docs/playtests/YYYY-MM-DD.md` и влияют на значения TUNABLE.

## 7. Метрики качества

| Метрика | Порог |
|---|---|
| Покрытие правил MUST тестами | 100% |
| Падения клиента на час | < 0.05 |
| Падения сервера | 0 за 7 дней (Closed Beta) |
| Время восстановления после падения сервера | < 2 мин |
| Время прохождения полного набора автотестов на PR | < 20 мин |
